# Файловая база данных

Справочники системного дизайна, из которых собираются задания для кандидатов. Все файлы — JSON в UTF-8, каждый содержит массив записей.

| Файл | Что хранит |
|---|---|
| `element_types.json` | Типы элементов схемы: UI, сервис, БД, очередь и т. д. |
| `link_types.json` | Виды связей между элементами |
| `element_instances.json` | Конкретные решения для каждого типа, реальные и выдуманные |
| `designs.json` | Системные дизайны: идентификатор, название, контекст |
| `design_structures.json` | Структура каждого дизайна: узлы и связи |
| `behaviors.json` | Поведения, которые программируемый узел обязан учесть в коде |
| `influence_channels.json` | Каналы влияния: как поведение распространяется по схеме |
| `api_problems.json` | Задача «проблемы API» для бэкендеров и аналитиков: API-ресурсы, проблемы с наблюдаемыми симптомами и решения, связанные с проблемами «многие ко многим». Объект из трёх массивов, а не один массив. Сервер его наружу не отдаёт: в нём ответы |
| `ux_problems.json` | Задача «проблемы интерфейса» для фронтендеров: контексты продуктов, компоненты с чертами, экраны из компонентов, проблемы компонентов и их взаимодействий, решения с побочными эффектами. Объект из восьми массивов. Сервер его наружу не отдаёт: в нём ответы |
| `qa_problems.json` | Задача «проблемы тестирования» для тестировщиков: системы со словарями для шаблонов, виды документов (артефактов), решения и проблемы трёх уровней с наблюдениями, документами-уликами, best practice, костылями и ошибочными ходами. Объект из пяти массивов. Сервер его наружу не отдаёт: в нём ответы |
| `fsp_competitions.json` | Выдуманные командные соревнования ФСП по продуктовому программированию, прошедшие и идущие: формат, уровень, даты, кейс партнёра, требуемый состав команды по ролям и стек. Ссылается на `fsp_team_roles.json` и `fsp_stack.json` |
| `fsp_future_competitions.json` | Будущие соревнования ФСП для имитации: те же поля и ещё `minutes_after_profile_link` — через сколько минут после связки профилей ITinder и ФСП пользователь будто бы в нём поучаствовал |
| `fsp_team_roles.json` | Роли в команде — участнице соревнования: бэкендер, фронтендер, тестировщик, системный аналитик; что каждая делает и что проверяет жюри |
| `fsp_stack.json` | Стек соревнований: языки, СУБД, способы интеграции и компетенции тестировщиков. Объект из четырёх массивов |
| `project_questionnaire.json` | Схема анкеты, по которой рекрутёр заводит IT-проект: выясняет, задан ли стек, уточняет заданный или подбирает недостающий под соискателей ITinder, и собирает вакансии. Ссылается на `fsp_stack.json`, `fsp_team_roles.json`, грейды и специализации `hat_replicas.json`. Объект, а не массив. Читают окно «Проекты и вакансии» и `app/tools/projects.py` |
| `companies/` | Компании-заказчики проектов, по файлу на компанию, имя файла — идентификатор. Общие для всех рекрутёров; новую создаёт сохранение проекта с названием, которого ещё нет. Две компании — для теста. Сервер отдаёт их только через API |
| `user_project_company/` | Проекты рекрутёров, по файлу на проект: кто завёл, компания, ответы анкеты, сводка, черновики вакансий до утверждения. Создаются, когда рекрутёр заполняет анкету в окне «Проекты и вакансии»; сервер их наружу не отдаёт |
| `projects_jobopenings/` | Утверждённые вакансии проектов, по файлу на вакансию. Создаются, когда рекрутёр утверждает список вакансий; сервер их наружу не отдаёт |
| `invitations/` | Приглашения, по файлу на приглашение: тип (направление), рекрутёр, кандидат, вакансия, снимок вакансии и история статусов. Создаются, когда рекрутёр отправляет приглашение в окне «Соискатели», а соискатель — отклик в окне «Вакансии»; сервер их наружу не отдаёт |
| `user_tests/` | Итоги тестов «Задачи на грейд», по файлу на тест, имя файла случайное. Создаются, когда кандидат отправляет ответ в окне теста; сервер их наружу не отдаёт |
| `ui_scheme.json` | Схема экранов приложения. Копия таблицы Supabase `itinder_ui_scheme` |
| `hat_replicas.json` | Реплики шляпы. Копия таблицы Supabase `itinder_hat_replicas` |
| `additional_desktop_icons.json` | Дополнительные значки рабочего стола «операционной системы»: `mode` — кому значок, `Applicant` соискателю, `Recruiter` рекрутеру (кто пользователь, видно по `user_specializations/`, см. `app/tools/desktop_icons.py`). Копия таблицы Supabase `itinder_additional_desktop_icons` |
| `users/` | Записи пользователей, по файлу на пользователя. Создаются регистрацией в интерфейсе, сервер их наружу не отдаёт |
| `user_specializations/` | Специализации и грейды пользователей, по файлу на запись. Создаются, когда пользователь соглашается с распознаванием резюме или выбирает сам (кнопка грейда); сервер их наружу не отдаёт |
| `user_names/` | Имена и фамилии пользователей, по файлу на пользователя. Создаются, когда пользователь вводит имя в окне «операционной системы» на мониторе комнаты; сервер их наружу не отдаёт |
| `user_fsp/` | Связка профиля с ФСП, по файлу на пользователя: ФСП ID, соревнования и подтверждённые ими компетенции со степенью подтверждения. Создаётся, когда пользователь в окне «Достижения в ФСП» соглашается дополнить профиль; сервер его наружу не отдаёт |
| `user_blocks/` | Соискатели, которые не хотят показываться в поиске рекрутёров, по файлу на пользователя: `{"user_id", "created_at"}`. Создаётся, когда соискатель включает тумблер «Скрыть профиль от рекрутёров» в окне «PDF-профиль» (значок `6`, `app/tools/profile_visibility.py`), и удаляется, когда выключает; такие файлы пишет и генератор соискателей. Спрятавшегося окно «Соискатели» (значок `9`) не показывает ни в графе команды, ни в поиске по вакансии, специализации и грейду, пригласить его нельзя; сервер файлы наружу не отдаёт |

Сгенерированные соискатели для разработки части рекрутера — `python app/tools/seed_applicants.py` (по умолчанию 500, `--count`, `--seed`; `--clean` — только удалить). Пишет файлы во все папки `user_*/` и `users/` в том же виде, что сервер; в `users/` у них поле `"seed": "seed_applicants"`, по нему каждый запуск удаляет прошлых сгенерированных, настоящих не трогает. Пароль у всех один — `PASSWORD` в скрипте.

Сгенерированные рекрутёры с проектами и вакансиями для демонстрации — `python app/tools/seed_recruiters.py` (по умолчанию 30, `--count`, `--seed`; `--clean` — только удалить). Пишет `users/` (поле `"seed": "seed_recruiters"`), `user_specializations/` (`Recruiter`, ручной выбор грейда на странице 6), `user_names/`, а компании, проекты и утверждённые вакансии — обычным путём `projects.create` → `projects.approve`, с теми же проверками, что у окна «Проекты и вакансии». Компании и проекты — вымышленные, из `COMPANIES` в скрипте: 32 компании разных отраслей и городов (компания с тем же названием, что уже есть в `companies/`, берётся готовая), 46 проектов — действующие системы с заданным стеком, у каждого рекрутёра хотя бы один. Вакансии собираются из стека проекта: позиции по клиентам (веб, Android, iOS, Flutter, React Native, 1С), грейды, требования со степенью подтверждения ФСП по грейду, задачи и задания по шаблонам, вилка по специализации, грейду, отрасли и городу. Часть проектов — с завершённым набором. Каждый запуск сначала удаляет прошлых сгенерированных рекрутёров вместе с их проектами, вакансиями, приглашениями на эти вакансии и компаниями, на которые больше нет проектов; настоящих пользователей не трогает. Пароль у всех один — `PASSWORD` в скрипте.

Анализ влияния: `python app/tools/influence.py > app/reports/influence_report.md`.

Ранжирование соискателей для рекрутёра — `app/tools/ranking.py`: по вакансии (`--vacancy <id в projects_jobopenings или путь к JSON>`) и по специализации и грейду (`--specialization Backend --grade Middle`, любое можно опустить); `--top N`, `--json`. Читает `user_specializations/`, `user_tests/`, `user_fsp/`, `user_names/`, `user_blocks/`, ничего не пишет. Алгоритм — в докстринге модуля. В интерфейсе — окно «Соискатели» рекрутёра (значок `9`, `app/tools/applicant_search.py`); при первом запуске оно показывает презентацию `app/assets/presentation/applicants/slides.json`.

Ранжирование вакансий для соискателя — `app/tools/vacancy_ranking.py <user_id>` (`--top N`, `--json`), зеркало `ranking.py`; ничего не пишет. В интерфейсе — окно «Вакансии» соискателя (значок `3`, `app/tools/vacancy_search.py`), см. раздел «Окно «Вакансии» соискателя» ниже; при первом запуске оно показывает презентацию `app/assets/presentation/vacancies/slides.json`.

## Обмен с Supabase

Копии таблиц Supabase — `ui_scheme.json`, `hat_replicas.json` и `additional_desktop_icons.json`. Список таблиц и файлов — `TABLES` в `app/tools/supabase_tables.py`, новая таблица добавляется туда одной строкой. Ключ берётся из `.env.local` в корне проекта, образец — `.env.example`.

Выгрузить таблицы в файлы: `python app/tools/supabase_pull.py`, только некоторые — по именам: `python app/tools/supabase_pull.py hat_replicas`. Файл перезаписывается целиком, и правки в нём, которые ещё не отправлены, пропадут.

Отправить правки файлов в таблицы: `python app/tools/supabase_push.py`, так же можно назвать таблицы. Без флагов скрипт только показывает, что добавится и какие поля изменятся (было → станет). Записывает с `--apply`. Строки, которых нет в файле, удаляются из таблицы только с `--delete`.
- Новая строка в файле — строка с `id`, которого нет в таблице. Этот `id` временный: номер выдаёт Supabase, а ссылки на строку внутри таблицы (`anchor_point_id` в схеме экранов) переписываются. После записи таблица выгружается обратно в файл.
- Если в таблице под тем же `id` строка с другим `created_at` (её добавили после выгрузки), скрипт остановится и ничего не затрёт.
- До обращения к таблице скрипт проверяет файл: повторы `id`, ссылки `anchor_point_id` на несуществующую строку или по кругу. В схеме экранов ещё цвета не вида `#RRGGBB` (в `background_hex` — и `##RRGGBB`) и `Layout` у `Page`, который не разбирается как JSON. В значках рабочего стола — `image`, под которым нет файла в проекте.
- Правки, сделанные в самой таблице после выгрузки, `--apply` перезапишет значениями из файла, поэтому сначала стоит посмотреть, что скрипт собирается поменять.
- Писать в таблицы может secret-ключ.

## ui_scheme.json

Копия таблицы `itinder_ui_scheme`, строки по возрастанию `id`.

| Поле | Описание |
|---|---|
| `id` | Идентификатор элемента |
| `created_at` | Когда строка создана в Supabase |
| `page` | Номер страницы |
| `image` | Путь к картинке |
| `background_hex` | Цвет фона, `#RRGGBB`. `##RRGGBB` — неоновый стиль в цвете `#RRGGBB`: у таблички по контуру стекла светится неоновая трубка, фон — тот же цвет почти погасший, текст и картинки светятся. Доска и клетка неона пока не умеют и берут цвет как обычный |
| `anchor_point_id` | Ссылка на `id` элемента, к которому привязан этот: элемент висит на цепи под ним. Пусто — корень страницы, он висит на анкерной точке станции. Дочерние элементы одного родителя раскладываются по строкам: блочные (картинка, заголовок с текстом) занимают строку целиком, кнопки (`Header and icon on the left`) и портретные карточки встают в ряд; каждая строка висит под предыдущей. Строка `Page` может изменить эту раскладку |
| `object_type` | Чем элемент выглядит в сцене. `A sign like the ones in the Moscow Metro` — двояковыпуклая стеклянная табличка на цепи. `Chalkboard` — школьная доска цвета `background_hex`, поле ввода: набранный текст пишется на ней мелом цвета `title_color`, рукописным шрифтом. `Oblong birdcage` — продолговатая клетка, поле пароля: каждый символ — белый шарик внутри. `Page` — не объект сцены, а настройки своей страницы (не больше одной строки на страницу): в `Layout` — корректировки сборки, остальные поля пустые |
| `Layout` | Как устроено содержимое объекта. `Full-object image` — контейнер с пропорциями картинки `image` на фоне `background_hex`. `Title and text` — заголовок `title` и текст `text` на фоне `background_hex`, высота контейнера по тексту. `Header and icon on the left` — кнопка: квадратная иконка `image` слева, заголовок `title` справа; одна в строке — растягивается вширь, содержимое по центру. `Headline only` — в контейнере только текст: у таблички заголовок `title` на фоне `background_hex`, у доски и клетки — введённый текст (`title`, если задан, — начальное значение). Табличка `Title and text` или `Headline only` шире строки растягивается вширь, шрифт тот же. `Portrait orientation. Large image with a caption underneath.` — вертикальная карточка: картинка `image` во всю ширину (место под неё не ниже 4:3 по высоте, чтобы и с квадратной картинкой карточка была вертикальной), под ней подпись `title` цвета `title_color` слева, всё на фоне `background_hex`; карточки встают в ряд, как кнопки. У строки `Page` — JSON с корректировками страницы, см. ниже |
| `title`, `title_color` | Заголовок и его цвет (`Title and text`, `Headline only`; у доски — цвет мела) |
| `text`, `text_color` | Текст и его цвет (для `Title and text`) |
| `link_to_page` | Номер страницы, которая открывается по клику на элемент. Пусто — элемент не ссылка |
| `additional action` | Что ещё делает клик по элементу. `Creating a user record` — регистрация: почта берётся с доски (`Chalkboard`) той же страницы, пароль — из клетки (`Oblong birdcage`), на странице должно быть ровно по одному такому полю; создаётся запись в `users/`, и пользователь становится текущим во вкладке; почта, которая уже есть в `users/` (без учёта регистра и пробелов по краям), — ошибка. `Authorization` — вход: почта и пароль берутся так же, с доски и из клетки той же страницы, и сверяются с записями в `users/`; не подошли — ошибка внизу экрана с кнопкой «Зарегистрироваться» (держится 10 секунд): она открывает страницу с элементами `Creating a user record`, ближайшую по номеру к текущей, по тому же правилу, что и ниже. Подошли — пользователь становится текущим во вкладке, и если у него уже есть запись в `user_specializations/`, он уходит в комнату, как после `Save selection and enter the room`; если нет — открывается та же страница, куда ведёт регистрация: `link_to_page` элемента `Creating a user record` на ближайшей по номеру к текущей странице с ним (сейчас 4 — выбор «соискатель / рекрутёр»), `link_to_page` самого элемента входа при этом не используется. `User resume recognition` — распознавание резюме: клик открывает выбор файла PDF (один, до 5 МБ), затем экран распределительной шляпы (реплики из `hat_replicas.json`): нейросеть определяет специализацию и грейд, пользователь соглашается — создаётся запись в `user_specializations/`, и пользователь уходит в комнату, как после `Save selection and enter the room`, — или загружает другое резюме, или возвращается к ручному выбору (действие отменено). `Save selection and enter the room` — ручной выбор: элемент — кнопка грейда, висит под карточкой специализации; создаётся запись в `user_specializations/` (грейд — `title` элемента, специализация — `title` элемента из его `anchor_point_id`, а на странице 6 — всегда `Recruiter`: там над кнопками грейда вопрос, а не карточка), потом камера подходит к дверям поезда напротив страницы, двери открываются, камера входит в вагон, экран гаснет и открывается комната — внутреннее приложение `resume3` (`/resume3/`, сборка из `resume3/public`). Оба действия с записью специализации требуют текущего пользователя. Если у элемента есть и `link_to_page`, страница открывается после успешного действия; у действий, которые уводят в комнату, ссылка не открывается |

## Layout строки Page

Корректировки сборки страницы по отношению к стандартной (как её описывают `anchor_point_id`, `object_type` и `Layout` элементов). JSON-объект в текстовом поле; пусто — страница собирается стандартно. Ошибка в JSON или неизвестное поле показывается на экране, а не пропускается молча. Читает `app/web/src/page/pageLayout.js`.

Все длины в метрах стандартной сборки, где строка во всю ширину — 2 м, цепь под элементом — 0,15 м, цепь от потолка до корня — 0,35 м. `scale` применяется к готовой странице.

| Поле | Описание |
|---|---|
| `version` | Версия формата, сейчас `1` |
| `scale` | Уменьшить собранную страницу целиком: таблички, фурнитуру, цепи. Камера подходит ближе, и на экране страница выглядит как неуменьшенная. Нужен, когда страница не помещается между потолком и платформой или в люк. По умолчанию `1` |
| `camera.mode` | Режим камеры у страницы. `eye` (по умолчанию) — камера на уровне глаз, 1,65 м, отходит настолько, чтобы страница поместилась в кадр, взгляд не задирался выше 16° и до страницы было не меньше 4 м. Страница у потолка поэтому видна издалека. `close` — камера подлетает на высоту середины страницы и смотрит на неё прямо, с расстояния, на котором страница как раз помещается в кадр |
| `rules` | Правила для элементов, применяются по порядку; поле из более позднего правила перекрывает раннее |
| `rules[].ids` | Каким элементам правило, массив `id` |
| `rules[].width` | Внешняя ширина элемента вместо его доли в строке (у корня — вместо 2 м) |
| `rules[].chain` | Длина цепи, на которой висит элемент (у корня — от потолка) |
| `rules[].suspension` | На скольких цепях висит табличка: `1` — за кольцо над центром (по умолчанию), `2` — по цепи на каждое верхнее ушко. Широкая табличка на двух цепях не перекашивается, если под одним её краем груза больше |
| `rules[].gap_before` | Зазор слева от элемента в его строке вместо `rows.gap` родителя — отделить элемент от соседей |
| `rules[].rows.flow` | Как раскладывать дочерние элементы: `auto` — стандартно, `row` — все в одну строку, `column` — каждый в своей строке, столбиком |
| `rules[].rows.width` | Ширина строк дочерних элементов (стандартно 2 м) или `"parent"` — как у самого элемента |
| `rules[].rows.gap` | Зазор между соседями в строке (стандартно 0,08 м) |
| `rules[].rows.chain` | Длина цепей дочерних элементов |

Пример — страница 5: заголовок `14` растянут в полосу на всю ширину ряда и висит на двух длинных цепях; пять карточек под ним в ряд, резюме `31` отодвинуто от специализаций; кнопки грейдов под каждой специализацией столбиком на коротких цепях; всё уменьшено до 0,58, чтобы страница прошла в люк между светильниками.

```json
{"version": 1, "scale": 0.58, "rules": [
  {"ids": [14], "width": 5.13, "chain": 2.75, "suspension": 2, "rows": {"width": "parent", "gap": 0.16}},
  {"ids": [15, 16, 17, 18], "rows": {"flow": "column", "width": "parent", "chain": 0.07}},
  {"ids": [31], "gap_before": 0.4}
]}
```

Пример — страница 4: две кнопки висят у самого потолка, на уровне глаз камера видела их за 9 м. Камера подлетает к ним:

```json
{"version": 1, "camera": {"mode": "close"}}
```

Люк над страницей расширяется под её ширину, но светильники стоят в 1,7 м от оси станции: страница шире 3 м заденет их при подъёме и спуске.

## influence_channels.json

Поведение возникает в узле (решение) или на конце `to` связи (вид связи) и распространяется по связям, перечисленным в `carriers`. Узлы типов из `transparent_types` пропускают влияние дальше. Первый непрозрачный программируемый узел на пути обязан поведение учесть. Непрозрачный непрограммируемый узел останавливает влияние, потому что учесть его не может.

| Поле | Описание |
|---|---|
| `id`, `name`, `description` | Идентификатор, название, описание |

## api_problems.json

Задача для бэкендеров и системных аналитиков: кандидату показывают API-ресурс и симптомы нескольких проблем сразу, все как равноправные, а он ищет решения (бэкендер ещё и пишет код). Число проблем зависит от грейда: Junior — 1, Middle — 2, Senior — 4. Ресурс выбирается случайно, затем случайные проблемы из применимых к нему. | Поле | Описание |
|---|---|
| `id`, `name`, `endpoint`, `description` | Идентификатор, название, метод и путь, что делает ресурс. Показываются кандидату |

`solutions[]` — варианты решений, из них кандидат выбирает:

| Поле | Описание |
|---|---|
| `id` | Идентификатор решения |
| `name`, `description` | Название и что решение делает. Показываются кандидату в списке выбора |

`problems[]`:

| Поле | Описание |
|---|---|
| `id` | Идентификатор проблемы |

## ux_problems.json

Задача для фронтендеров: кандидату показывают компонент или экран интерфейса в контексте продукта и симптомы нескольких проблем, все как равноправные, а он ищет решения. | Поле | Описание |
|---|---|
| `id`, `name`, `description` | Идентификатор, название и что решение делает. Показываются кандидату в списке выбора; описание нейтральное, без оценки |
| `bad_in` | Необязательно. Теги контекстов, в которых решение не подходит: там оно не засчитывается, даже если указано в `fixes` |
| `side_effects` | Необязательно. Какие проблемы решение создаёт на экране: `{"problem", "when"?, "with"?}`. `problem` — проблема со `scope` `side_effect`; `when` — условие (см. ниже); `with` — эффект возникает, только если выбрано ещё и это решение. Если у проблемы побочного эффекта пустой `fixes`, решение на таком экране не засчитывается никогда |
| `distracts` | Необязательно. Проблемы, для которых это правдоподобный, но неверный вариант: решение попадает в список выбора, когда такая проблема применима на экране |

`problems[]`:

| Поле | Описание |
|---|---|
| `id` | Идентификатор проблемы |
| `scope` | `component` — проблема внутри компонента; `link` — во взаимодействии двух компонентов; `side_effect` — кандидату не показывается, её создаёт решение другой проблемы |
| `category` | Раздел для авторов: `network`, `rendering`, `layout`, `focus`, `state`, `forms`, `a11y`, `media` |
| `name` | Суть проблемы. Кандидату не показывается; нужна авторам и проверяющей нейросети |
| `symptoms` | У `component`: объект «`components.id` → текст симптома»; проблема применима только к этим компонентам. Симптом описывает только наблюдаемое, без причины и без названий решений |
| `applies`, `symptom` | У `link`: `{"a": [черты], "rel": связь, "b": [черты]}` — к каким парам узлов применима проблема, и шаблон симптома с формами названий `{a[gen]}`, `{b[Layer]}`… На каждый узел `a` берётся одна пара — с ближайшим подходящим `b` |
| `description` | У `side_effect`: что случится — показывается кандидату в итоге проверки, если он не закрыл этот эффект |
| `when` | Необязательно. Условие применимости (см. ниже) |
| `fixes` | Решения, которые устраняют проблему. Не пусто, кроме `side_effect`: там пусто, если эффект неустраним |
| `mitigates` | Решения, которые только смягчают; не пересекается с `fixes` |
| `confusable_with` | Кроме `side_effect`. Проблемы со схожими симптомами, связь взаимная. Вместе в задание не попадают |

Условие `when` — объект, все его поля должны выполняться. Узел условия — тот, к которому применено решение: у проблемы компонента — сам компонент, у проблемы взаимодействия — узел `a`.

| Поле | Выполнено, если |
|---|---|
| `tags_any`, `tags_none` | У контекста есть хотя бы один из тегов / нет ни одного |
| `rows_min`, `rows_max` | `rows` контекста не меньше / не больше |
| `ancestor_trait`, `no_ancestor_trait` | Узел находится / не находится внутри компонента с этой чертой |
| `contains_trait` | Внутри узла есть компонент с этой чертой |
| `screen_trait` | На экране есть компонент с этой чертой |
| `screen_min` | `{черта: n}` — на экране не меньше `n` компонентов с этой чертой |

Связи с решениями не зависят от компонента: симптомы написаны так, чтобы `fixes` и `mitigates` подходили к каждому компоненту из `symptoms`. Если для какого-то компонента решение подходит иначе, проблему нужно разделить на две.

## qa_problems.json

Задача для тестировщиков (QA). Кандидату показывают систему, наблюдения команды — что заметили, без причины, — и документы к каждому наблюдению: требование, тест-кейсы, баг-репорт, обращение клиента, код автотеста, лог CI, конфигурацию пайплайна, метрики, разбор инцидента. Причина видна в документах, кандидат ищет решение и отличает его от костыля. Задание собирает `app/tools/qa_tasks.py` процедурно, без нейросети: система, набор проблем уровня грейда (Junior — 1, Middle — 2, Senior — 4), зерно; от зерна зависят числа в документах (номера сборок, доли падений, время), и по ключу задания оно собирается заново таким же. Отвечают и проверяются так же, как в `api_problems.json` (`app/tools/grade_tests.py`), но выбранный костыль или ошибочный ход портит решение проблемы. Объект из пяти массивов. Сервер его наружу не отдаёт: в нём ответы. Проверка справочника (все шаблоны во всех применимых системах) и число наборов проблем: `python app/tools/qa_tasks.py`; задание с эталоном и документами: `python app/tools/grade_tests.py QA Middle --artifacts`.

`tags[]` — особенности систем: `id`, `name`; `name` показывается кандидату.

`systems[]` — что тестируют:

| Поле | Описание |
|---|---|
| `id`, `name`, `description` | Идентификатор, название и описание системы. Показываются кандидату |
| `tags` | Особенности, ссылки на `tags.id`. Показываются кандидату; от них зависит, применима ли проблема (`when`) |
| `vars` | Словарь для шаблонов: строки, списки и вложенные объекты — `{s[range][max]}`, `{s[tests]}`. Сгруппирован по темам: `range` (поле с диапазоном), `flow` (обращение клиента), `loc` (баг между фронтендом и бэкендом), `triage`, `states`, `combo`, `ambig`, `shared`, `async`, `time`, `ui`, `api_check`, `env`, `stage`, `ext`, `unique`, `contract`, `prod`, `pd`, `peak` и общие `app`, `svc`, `repo`, `prefix`, `rules_topic`, `tests`. Значения повторно не форматируются, поэтому код и JSON с фигурными скобками держат здесь. Какие поля нужны — видно по шаблонам проблем; чего не хватает, покажет проверка справочника |

`artifacts[]` — виды документов: `id`; `name` — как вид называется у кандидата («Лог CI», «Баг-репорт»); `format` — `text` (абзацы, строки переносятся) или `code` (моноширинно, без переноса: логи, код, таблицы).

`solutions[]`:

| Поле | Описание |
|---|---|
| `id`, `name`, `description` | Идентификатор, название и что решение делает. Показываются кандидату в списке выбора; описание нейтральное — по нему не видно, костыль ли это |
| `distracts` | Необязательно. Проблемы, для которых это правдоподобный, но бесполезный вариант: решение попадает в список выбора, когда такая проблема применима к системе. Выбор не мешает, но считается лишним |

`problems[]`:

| Поле | Описание |
|---|---|
| `id` | Идентификатор проблемы |
| `level` | `Junior` — тест-дизайн, локализация и оформление багов, требования; `Middle` — автоматизация, API и БД, флаки-тесты, окружения и тестовые данные; `Senior` — стратегия, пирамида, CI/CD, процессы (Shift-Left, Shift-Right), контракты, нагрузка. Задание грейда собирается только из проблем его уровня |
| `area` | Раздел для авторов: `test_design`, `bugs`, `requirements`, `flaky`, `ui_automation`, `api`, `environment`, `test_data`, `strategy`, `contracts`, `process`, `ci_cd`, `production`, `performance` |
| `name` | Суть проблемы. Кандидату не показывается; нужна авторам и проверяющей нейросети |
| `when` | Необязательно. `tags_any` / `tags_none` — у системы есть хотя бы один из тегов / нет ни одного. Иначе проблема применима ко всем системам |
| `params` | Необязательно. Числа и выборки для шаблонов, по имени: `{"int": [от, до], "step"?}`, `{"pick": [варианты]}` (вариант — число, строка, список или объект: `{timing[fail]}`), `{"clock": [час от, час до]}` — время «ЧЧ:ММ:СС», `{"sample": "список из vars", "k": n}` — n разных элементов (`{noise[0]}`). Берутся из зерна, системы и проблемы. Имя `s` занято словарём системы |
| `observation` | Шаблон наблюдения — что видит кандидат: только наблюдаемое, без причины и названий решений |
| `evidence` | Варианты документов: массив вариантов, вариант — массив документов `{"artifact", "title", "lines"}`; `lines` — строки шаблона. В задание попадает один вариант, он выбирается по зерну |
| `fixes` | Best practice: решения, которые устраняют причину. Не пусто |
| `mitigates` | Решения, которые только смягчают |
| `crutches` | Костыли: `{"solution", "why"}` — решение прячет симптом, а причина остаётся; `why` (шаблон) показывается кандидату в итоге, если он выбрал костыль. Выбран только костыль — итог «костыль», вместе с устраняющим решением — «решено частично» |
| `wrong` | Необязательно. Ошибочные ходы: `{"solution", "why"}` — решение противоречит тому, что видно в документах (например, баг передан не той команде). Только он — «не решено», вместе с устраняющим решением — «решено частично» |
| `confusable_with` | Проблемы, которые вместе в задание не попадают: у них совпадают решения или улики. Связь взаимная |

Одно решение в `fixes`, `mitigates`, `crutches` и `wrong` одной проблемы встречается не больше одного раза. Связи с решениями не зависят от системы: шаблоны написаны так, чтобы эталон подходил к каждой системе, где проблема применима.

Шаблоны — `str.format`: `{s[группа][поле]}` — словарь системы, `{имя}` — `params`, `{имя:>6}` — с выравниванием. Фигурная скобка в самом шаблоне удваивается: `{{`, `}}`.

## project_questionnaire.json

Схема анкеты IT-проекта для рекрутёра. Анкету считает окно «Проекты и вакансии» (значок `8` в `additional_desktop_icons.json`, `portfolio-inner-site/src/projectQuestionnaire.ts`), вакансии проверяет и записывает `app/tools/projects.py`. До анкеты окно спрашивает название проекта и компанию (`prelude`). Порядок такой:

1. «Проект», «Клиенты и платформа», «Ограничения по стеку», «Действующая система», «Системы партнёров», «Стандарт компании» выясняют, задан ли стек: действующий код, нативное мобильное приложение, 1С или Битрикс, способы обмена с системами партнёров, стандарт компании, отечественное ПО.
2. «Что делает продукт», «Тестирование», «Требования» спрашивают о продукте простыми словами. Вопрос о виде стека, который уже задан целиком, не показывается.
3. Ответы дают эффекты: `fix` — компетенция задана, `need` — нужна компетенция такого рода (кандидаты из `fsp_stack.json`), `prefer` — какие кандидаты лучше и почему, `role` — нужна роль, `open_question` — вопрос техлиду.
4. Шаблоны дополняют анкету: `fixed_details` — по блоку на каждую заданную компетенцию (кому нужна, обязательна ли, какая степень подтверждения в ФСП), `market_choices` — по блоку на каждую потребность с несколькими кандидатами, отсортированными по числу соискателей ITinder с этой компетенцией в `user_fsp/`.
5. «Команда» — сколько людей нанять по позициям (роль с направлением: веб, Android, iOS, 1С…) и грейдам, с советами по составу. `scarcity` — что делать с заданной компетенцией, под которую мало соискателей.
6. `vacancies` — по блоку на позицию × грейд: название, задача, требования к стеку. Формат готовой вакансии и правило поиска соискателей под неё — в поле `vacancy`.

| Поле | Описание |
|---|---|
| `version`, `id`, `title`, `description` | Версия схемы, идентификатор и назначение анкеты |
| `references` | Откуда берутся специализации, грейды, роли, стек и степени подтверждения |
| `syntax` | Типы вопросов, условия показа (`show_if`, `when`), эффекты ответов, шаблоны |
| `rules` | Правила: какие компетенции доступны роли, позиции, степень по грейду, отечественные СУБД, близкие компетенции, варианты мобильного приложения, слияние потребностей |
| `sections[]` | Разделы с вопросами; раздел с `repeat` — шаблон, повторяется для каждого элемента вычисленного списка |
| `derived[]` | Вычисляемые значения: заданный стек, режим по видам стека, позиции, потребности, варианты выбора, вакансии, открытые вопросы |
| `market` | Как считать рынок: соискатели, их грейд и компетенции, число подходящих, уровни дефицита, score варианта |
| `vacancy` | Формат вакансии, правило поиска соискателей под неё и пример |
| `storage` | Где хранятся ответы и вакансии: `user_project_company/` и `projects_jobopenings/` |

## user_project_company/

Файл `<id>.json` на проект, создаёт `app/tools/projects.py` по `POST /api/projects`, когда рекрутёр заполнил анкету. Порядок такой:

1. Рекрутёр вводит название проекта и выбирает компанию (или вводит новую), проходит анкету. Какие вопросы показать и какие вакансии получаются, считает окно по `project_questionnaire.json`.
2. Анкета заполнена — файл проекта: ответы, сводка и черновики вакансий (`vacancies_draft`). Статус «Вакансии не утверждены».
3. Рекрутёр правит список: название, грейд, число людей, зарплатная вилка (обязательна), чем займётся, требования к стеку, задания, что ещё сказать; добавляет и удаляет вакансии. Утверждает — файлы в `projects_jobopenings/`, `vacancies_draft` становится `null`, статус «Набор идёт». Утверждать можно снова: вакансии с прежним `id` перезаписываются, убранные из списка — удаляются.
4. «Набор завершён» — `completed_at`; пока набор завершён, вакансии не правятся. «Возобновить набор» снимает отметку.

Копия проекта — новый файл с той же компанией и ответами, вакансии — черновиком (`copied_from` — откуда). Удаление проекта удаляет и файлы его вакансий. Проект видит и меняет только рекрутёр, который его завёл. Локальный снимок папки хранится в git; сервер не отдаёт эти файлы напрямую.

В общем поиске окна «Соискатели» (значок `9`, режим поиска по специализации и грейду) приглашение недоступно без открытой вакансии подходящей специализации. Кнопка «Сгенерировать тестовые проекты и вакансии» находится в стартовом меню окна «Соискатели», рядом с выбором способа поиска, и доступна в том числе при наличии сохранённых или открытых вакансий. Эта же кнопка есть на главном экране окна «Проекты и вакансии» (значок `8`), над списком проектов; после генерации там обновляются проекты и каталог компаний, а существующее выделение сохраняется. Если у рекрутёра нет открытых вакансий вообще, экран поиска объясняет причину и указывает, что генерация доступна в стартовом меню. Кнопка вызывает `POST /api/applicants/test-projects {"user_id"}` (`app/tools/test_projects.py`): создаёт проекты «Тестовый проект: интернет-магазин» и «Тестовый проект: платформа аналитики», по четыре вакансии — Backend, Frontend, QA и Syst. Analyst. В наборе есть грейды Junior, Middle и Senior, зарплатные вилки в RUB, задачи, требования к стеку и вакансии с заданиями и без них. Генератор использует обычные `projects.create` и `projects.approve`, поэтому проекты и вакансии связаны, принадлежат рекрутёру и сразу доступны для приглашений.

`summary.test_generation` хранит версию и идентификатор шаблона тестового проекта. Каждый запрос добавляет ещё два проекта и восемь вакансий с новыми UUID, даже если у рекрутёра уже есть открытые тестовые вакансии. Прежние проекты и вакансии, их копии, ручные изменения и существующие приглашения сохраняются. После ошибки утверждения генератор может продолжить собственный черновик, только если тот в точности соответствует шаблону; изменённый черновик сохраняется. После генерации окно обновляет список вакансий, сохраняя текущие фильтры поиска. В выпадающем списке приглашения из поиска по специализации и грейду у каждой вакансии видна отметка «с заданием (N)» / «с заданиями (N)» или «без заданий». Ответ API: `created_projects`, `created_vacancies` — сколько создано в этом запросе; `project_ids`, `vacancy_ids` — идентификаторы нового набора, включая восстановленный после ошибки черновик.

| Поле | Описание |
|---|---|
| `id` | Идентификатор проекта; совпадает с именем файла |
| `user_id` | Рекрутёр: `users/<id>.json`, у которого есть специализация `Recruiter` |
| `company_id` | Ссылка на `companies/<id>.json` |
| `name` | Название проекта |
| `questionnaire` | `{"id", "version"}` анкеты, по которой даны ответы |
| `answers` | Ответы анкеты: `{id вопроса: ответ}`, ответы блоков шаблонов — `"<раздел>[<ключ>].<вопрос>"`. Только видимые вопросы |
| `summary` | Сводка окна: `stack_mode`, `kind_mode`, `mobile_variant`, `positions`, `fixed_stack` (заданный стек и кому он нужен), `choices` (потребности, кандидаты, выбор и рекомендованный), `team_plan`, `open_questions` — `[{"text", "blocking", "origin", "resolved"}]` |
| `vacancies_draft` | Черновики вакансий до утверждения (формат — `vacancy` в `project_questionnaire.json`, без полей файла); после утверждения — `null` |
| `vacancy_ids` | Утверждённые вакансии: имена файлов в `projects_jobopenings/` |
| `approved_at`, `completed_at` | Когда вакансии утверждены последний раз и когда набор завершён; `null` — нет |
| `copied_from` | Из какого проекта копия; `null` — не копия |
| `created_at`, `updated_at` | ISO 8601 в UTC |

## projects_jobopenings/

Файл `<id>.json` на утверждённую вакансию, пишет `app/tools/projects.py` по `POST /api/projects/vacancies`. Формат — `vacancy` в `project_questionnaire.json`: позиция, специализация и грейд, `count` — сколько людей одной роли, `task`, `requirements` (компетенции `fsp_stack.json` со степенью подтверждения в ФСП), `assignments` — задания (суть каждого текстом рекрутёра), `salary` — вилка `{from, to, currency}`, обязательна; `company`, `project` (название и ответы раздела «Проект»), `open_questions`, `status` (`draft` — есть нерешённые блокирующие вопросы, `ready`), `approved_at`. Завершён ли набор, смотрите в проекте. Локальный снимок папки хранится в git; сервер не отдаёт эти файлы напрямую.

## invitations/

В карточке нового отклика (`От кандидата рекрутеру` / `Соискатель - Рекрутёр`, статус `sent`, а для записей без заданий также `read`) есть «Принять отклик» и «Отклонить отклик». `POST /api/projects/feedback/respond {user_id, project_id, invitation_id, action, expected_revision}` с `action: "accept"` дописывает `accepted`, с `action: "decline"` — `declined`. Прямой ответ доступен новым откликам с заданиями и без них; записи в стадиях проверки решения проходят прежний процесс через эксперта. `GET /api/projects/feedback` возвращает `can_respond_application`. После ответа обновляются дерево, новости и число принятий вакансии; положительный ответ показывает e-mail кандидата и учитывается как найм. Снимок, задания, ответы и прежняя история сохраняются, отметка просмотра соискателя не меняется: новый статус вызывает у него уведомление. Чужие/удалённые связи не допускаются, повторные ответы и устаревшие версии дают `409` без записи.

В карточке проекта окна `8` есть вкладка «Обратная связь». При открытии проекта с непустыми новостями в таблице (или с новыми событиями в ответе открытия) она выбирается по умолчанию, до подтверждения просмотра принятия; иначе открывается «Вакансии». На вкладке двухуровневое дерево: вакансия с требуемым числом людей и числом принятий, ниже — связанные приглашения и отклики с именем кандидата, типом, текущим статусом и релевантностью. Выбор записи открывает её карточку со снимком заданий, решениями и историей. E-mail кандидата сервер возвращает только в `accepted`. Дерево обновляется каждые 15 секунд и при возвращении фокуса, сохраняя выбранную запись.

`GET /api/projects/feedback?user_id=<id>&project_id=<id>` (`app/tools/project_feedback.py`) возвращает `vacancies` с `invitations`. Релевантность рассчитывается той же `ranking.by_vacancy`, что и в окне «Соискатели» (`9`), по актуальной вакансии и текущему профилю кандидата: `100 × (0.35 × соответствие грейда + 0.65 × соответствие стека)`. Учитываются сданные тесты, достоверность заявленного грейда, степень компетенций ФСП и требования вакансии. Если кандидат уже не доступен для поиска, показывается сохранённая релевантность отправки или «нет данных».

Для `task_sent_for_review` в карточке доступна кнопка «Отправить эксперту на проверку» и форма e-mail. `POST /api/projects/feedback/review {user_id, project_id, invitation_id, action, email?, expected_revision}` с `action: "send"` проверяет адрес, сохраняет `expert_review` и дописывает `task_needs_review`; интерфейс сообщает об отправке. Письмо не отправляется: это имитация. Далее доступны «Эксперт отклонил решение» (`action: "reject"` → `solution_rejected`) и «Эксперт утвердил решение» (`action: "approve"` → `accepted`). Оба направления записей проходят эту проверку, задания берутся из снимка приглашения. История, снимок и решения сохраняются, `applicant_seen` не меняется, поэтому соискатель видит новый статус как новость. Действия доступны только владельцу проекта, выполняются под общей блокировкой; устаревшая версия и повторное решение дают `409` без изменения файла.

Когда число приглашений и откликов в `accepted` достигает `count`, у вакансии появляется «Закрыть вакансию». `POST /api/projects/feedback/close {user_id, project_id, vacancy_id}` сохраняет `closed_at` в файле вакансии и показывает «Закрыта наймом». Вакансия и приглашения не удаляются. Закрытие без заполненных мест даёт `409`; повторное закрытие сохраняет прежнюю дату. Отметка сохраняется при правке исходной вакансии и не переносится в копию проекта. Поиск и тестовая генерация исключают вакансии с `closed_at`, как и вакансии с уже заполненными местами.

На главном экране окна «Проекты и вакансии» (значок `8`) кнопка «Сгенерировать тестовую обратную связь» появляется, если у рекрутёра есть хотя бы одна существующая вакансия, связанная с его проектом, которую ещё не заполнили наймом: число приглашений в `accepted` меньше `count`. Удалённые вакансии, чужие проекты и черновики без файлов вакансий не учитываются. Завершение набора по проекту и блокирующие вопросы сами по себе не исключают существующую вакансию — это условие тестовой генерации. `GET /api/projects` возвращает для каждой строки `valid_vacancies` с числом таких вакансий.

Кнопка вызывает `POST /api/projects/test-feedback {"user_id"}` (`app/tools/test_feedback.py`). Используются только уже созданные пользователи с `seed: "seed_applicants"`, доступные для поиска и имеющие нужную специализацию; новые аккаунты не создаются. На каждую подходящую вакансию добавляется один исходящий отклик соискателя в `sent` и один ответ на приглашение рекрутёра: без заданий — `accepted`, с заданиями — текстовые `assignment_answers` и `task_sent_for_review`. Каждое второе решение также проходит стадию пересылки на проверку IT-специалисту (`task_needs_review`). Если тестовому кандидату уже отправили приглашение и он ещё не ответил, генератор дописывает его историю, сохраняя снимок вакансии. Иначе создаёт новое приглашение с ответом от другого доступного тестового кандидата. Обычные пользователи и их приглашения не изменяются.

Принятия учитываются как найм и могут закрыть вакансию. Повторные нажатия добавляют новые отклики и ответы для оставшихся подходящих вакансий; пара вакансия–соискатель не повторяется. Если вакансии закрыты наймом, тестовых кандидатов нет или подходящие кандидаты закончились, API возвращает понятную ошибку `409` без записи данных. Пакет выполняется под блокировкой приглашений, при ошибке записи откатываются новые файлы и изменения старых. Ответ содержит `created_applications`, `accepted_invitations`, `submitted_assignments`, `forwarded_assignments`, `created_invitations`, `updated_invitations`, `invitation_ids`. После генерации окно обновляет таблицу и новости, сохраняя выделение проекта.

В таблице окна «Проекты и вакансии» (значок `8`) колонка «Новости» показывает для каждого проекта три плашки. «Есть новые отклики» — связанные отклики соискателей в `sent`. «Есть принятие приглашения» — непросмотренные принятия (`accepted`) приглашений рекрутёра без задания. «Есть задания требующие проверки» — связанные приглашения с заданиями в `task_sent_for_review` или `task_needs_review`, независимо от направления. Учитываются только записи текущего рекрутёра, для которых сохранилась вся связь приглашение → вакансия → его проект; завершение набора не скрывает новости. Поддерживаются основные значения `type` и прежние обозначения `Соискатель - Рекрутёр` / `Рекрутёр - Соискатель`.

Считает `app/tools/project_news.py`: `GET /api/projects` добавляет к каждой строке `news` со счётчиками `new_applications`, `accepted_invitations`, `assignments_to_review`; `GET /api/project` также возвращает `accepted_news` — список `{id, revision}` непросмотренных принятий на момент открытия. Эти запросы ничего не записывают. После успешного открытия проекта окно вызывает `POST /api/projects/news/read {user_id, project_id, accepted_news}`. Только совпавшие версии принятых приглашений без задания получают `recruiter_seen`; новые принятия после открытия остаются новостями. Отклики и задания сохраняют плашки до смены соответствующего статуса. Таблица обновляется каждые 15 секунд и при возвращении фокуса в браузер, сохраняя выделенный проект.

Файл `<id>.json` на приглашение, создаёт `app/tools/invitations.py` по запросу `POST /api/invitations` к `app/tools/serve.py`, когда рекрутёр в окне «Соискатели» (значок `9`) отправляет приглашение. Пригласить можно своего соискателя на свою вакансию: вакансия готова (`status` `ready`), набор по проекту не завершён, вакансия не закрыта (принятых приглашений меньше `count`), у соискателя есть специализация вакансии, он не в `user_blocks/` и это не сам рекрутёр. Одного соискателя на одну вакансию приглашают один раз — даже если он отказался. Отклик соискателя — запись того же формата с `type` `От кандидата рекрутеру`, её создаёт `app/tools/vacancy_search.py` по `POST /api/vacancies/apply` из окна «Вакансии» (значок `3`). Окно соискателя «Приглашения» (значок `4`, `app/tools/applicant_invitations.py`) дописывает историю, решения и отметку просмотра в тот же файл; изменения сохраняются атомарно. Локальный снимок папки хранится в git; сервер не отдаёт эти файлы напрямую.

| Поле | Описание |
|---|---|
| `id` | Идентификатор приглашения, UUID v4; совпадает с именем файла |
| `type` | Тип (направление): `От рекрутера кандидату` — приглашение или `От кандидата рекрутеру` — отклик; прежнее обозначение отклика `Соискатель - Рекрутёр` тоже читается. По типу окно «Приглашения» (значок `4`) делит записи на вкладки «Приглашения» и «Отклики», а окно `8` — на приглашения и отклики с «Принять/Отклонить отклик». Окно «Соискатели» (значок `9`) всегда создаёт `От рекрутера кандидату`, окно «Вакансии» (значок `3`) — `От кандидата рекрутеру`; на одну пару «вакансия — соискатель» бывает только одна запись любого типа |
| `recruiter_id`, `applicant_id` | Рекрутёр и кандидат: `users/<id>.json`; направление задаёт `type` |
| `project_id`, `vacancy_id` | Проект (`user_project_company/`) и вакансия (`projects_jobopenings/`) |
| `vacancy` | Снимок файла вакансии на момент отправки, без `user_id`, `created_at`, `updated_at`: рекрутёр может поправить вакансию, а соискатель увидит то, на что его звали, вместе с заданиями (`assignments`) |
| `relevance` | Релевантность соискателя вакансии в момент отправки, 0–100 (`app/tools/ranking.py`) |
| `source` | Откуда отправлено: `team` — граф команды проекта, `vacancy` — поиск по вакансии, `search` — поиск по специализации и грейду, `vacancies` — отклик соискателя из окна «Вакансии» |
| `flow` | Набор статусов: `plain` — у вакансии нет заданий: `sent` Отправлено, `read` Просмотрено, `accepted` Принято, `declined` Отклонено; `assignment` — задания есть: `sent` Отправлено, `declined` Отклонено, `task_needs_review` Задание требует проверки, `task_sent_for_review` Задание отправлено на проверку, `solution_rejected` Решение отклонено, `accepted` Принято |
| `status_history` | История смены статусов `[{"status", "at"}]`, `at` — ISO 8601 в UTC; нынешний статус — последний. Отправка пишет `sent`; просмотр входящего без заданий — `read`, принятие — `accepted`, отказ — `declined`, отправка решений — `task_sent_for_review`. Прежние записи сохраняются |
| `assignment_answers` | Ответы соискателя на задания: массив многострочных текстов в порядке `vacancy.assignments`, появляется при отправке решений. Каждый ответ обязателен, до 5000 символов |
| `applicant_seen` | Последний просмотренный статус `{"status", "at", "revision"}`, где `revision` — длина истории. Новая запись или изменившийся последний статус/время/длина истории снова включает уведомление |
| `applicant_alert_seen` | Версия `{"status", "at", "revision"}`, показанная при входе соискателя в окно «Приглашения»: гасит только восклицательный знак у значка `4`, отметка «Новое» у записи остаётся до её просмотра (`applicant_seen`). Новый статус снова включает знак |
| `recruiter_seen` | Версия принятого приглашения без задания, просмотренная рекрутёром при открытии проекта: `{"status", "at", "revision"}`. Не зависит от `applicant_seen`, не меняет историю и решения; новое принятие снова включает плашку в колонке «Новости» |
| `test_feedback` | Метка генерации обратной связи: `{"version": 1, "batch": "UUID"}`. Обновляется только у новых записей и ответов уже созданных тестовых пользователей |
| `expert_review` | Имитация передачи эксперту: `email`, `sent_at`, `simulated: true`; после решения также `decision` (`approve`/`reject`) и `decision_at`. Старые записи, уже в `task_needs_review`, можно проверять и без этой метки |
| `test_generation` | Только у тестовых записей: версия генератора, идентификатор пакета и сценарий. Демонстрационные рекрутёр, компания, проект и вакансия хранятся в снимке с отдельными UUID; их идентификаторы не ссылаются на реальные рабочие записи |
| `created_at` | Когда отправлено, ISO 8601 в UTC |

Кто отказался (`declined`) или чьё решение отклонено (`solution_rejected`), в граф команды на эту вакансию больше не попадает.

Окно значка `4` оформлено в стиле Windows 95. Первый уровень вкладок — входящие «Приглашения» и исходящие «Отклики» (`От кандидата рекрутеру`; также читается прежнее обозначение `Соискатель - Рекрутёр`). Второй — объединение всех статусов из обоих наборов; рядом с вкладками показаны количества. У входящих приглашений вкладка статуса `sent` называется «Получено». Соискатель принимает или отклоняет только входящие приглашения в `sent`/`read`. Для принятия с заданиями он заполняет отдельное многострочное поле на каждое задание; отправленные решения переводят приглашение в `task_sent_for_review`. Отклики доступны только для просмотра статуса. У набора `assignment` нет `read`: просмотр подтверждает уведомление, сохраняя текущий статус.

`GET /api/applicant/invitations?user_id=<id>` возвращает только относящиеся к пользователю записи со снимками вакансий, историей, ответами, признаками `unseen`/`can_respond`, текущей версией `revision` и справочниками; чтение списка ничего не записывает. Выбор записи вызывает `POST /api/applicant/invitations/read {"user_id", "invitation_id", "expected_revision"}`. Вход в окно вызывает `POST /api/applicant/invitations/dismiss-alert {"user_id", "shown": [{"id", "revision"}]}` (до 1000 версий за запрос) и отвечает `{"dismissed", "alert"}`; чужие, удалённые и изменившиеся после показа версии пропускаются. Ответ — `POST /api/applicant/invitations/respond {"user_id", "invitation_id", "action", "answers"?, "expected_revision"}`, где `action` — `accept`/`decline`. Чужая запись даёт 404, устаревшая версия — 409; повторные переходы и изменение исходящего отклика запрещены.

Красный «!» рядом с иконкой `4` виден, пока есть хотя бы одно новое приглашение или непросмотренный статус приглашения/отклика. Вход в окно — открытие или возврат из свёрнутого на панели задач — гасит знак для всех показанных версий до появления нового приглашения или смены статуса одного из прежних. Отметки «Новое» у самих записей остаются, пока запись не выбрана. После просмотра и входа значки обновляются; новые изменения обнаруживаются опросом примерно раз в 15 секунд, в том числе при закрытом окне, и при возвращении на страницу.

В верхней панели окна всегда доступна кнопка «Сгенерировать тестовые приглашения». `POST /api/applicant/invitations/test-data {"user_id"}` (`app/tools/test_invitations.py`) создаёт новый пакет из 20 файлов: по 10 входящих приглашений и исходящих откликов. В каждом направлении есть все четыре сценария `plain` и все шесть `assignment`. История начинается с `sent` и последовательно доходит до выбранного статуса с возрастающими датами; после отправки заданий в записи есть примеры многострочных решений. Заданий бывает одно, два или три. Новые записи относятся только к выбранному пользователю и вызывают уведомление на значке. Тестовые названия отмечены `[Тест]`; отдельные UUID в снимках позволяют проверять принятие приглашений без закрытия настоящих вакансий. Каждый следующий запрос добавляет ещё 20 записей, не перезаписывая прежние приглашения, проекты, вакансии или аккаунты. При ошибке записи незавершённый пакет удаляется. Ответ: `created_invitations` и `invitation_ids`. После генерации окно обновляет счётчики и список, сохраняя введённые решения.

## Окно «Вакансии» соискателя

Значок `3` в `additional_desktop_icons.json` (режим `Applicant`), окно `portfolio-inner-site/src/components/applications/Vacancies.tsx` в стиле Windows 95: слева открытые вакансии по релевантности, справа карточка выбранной — почему она на этом месте, чего не хватает, требования и сильные стороны, проект и задания. Фильтры: специализация (если их несколько), грейд, «Ещё не откликался», поиск по названию, компании и технологии; порядок — по релевантности, зарплате или очереди. При первом запуске (у пользователя в этом браузере один раз) окно показывает презентацию о ранжировании; кнопка «Как считается» показывает её снова.

Ранжирует `app/tools/vacancy_ranking.py` — алгоритм в докстринге модуля. Жёсткий отбор один — специализация: вакансии тех специализаций, что есть у соискателя в `user_specializations/`; вакансия открыта (проект утверждён, набор не завершён, `status` `ready`, не закрыта наймом) и не своя. Релевантность 0–100 из трёх частей:

- **подхожу** — релевантность соискателя у рекрутёра (`ranking.by_vacancy`) / 100: тот же грейд по доказательствам, стек по ФСП и разбор требований;
- **подходит** — `65 % × сильные стороны + 35 % × уровень`: какая доля сильных компетенций ФСП соискателя (от сильной к слабой, каждая следующая на 30 % легче) нужна вакансии — обязательное целиком, желательное наполовину, близкая со скидкой; уровень — ступень вакансии относительно своего грейда: своя 1, выше 0,8, ниже 0,3, через ступень 0,2 и 0. Нет связки с ФСП или своего грейда — 0,5;
- **очередь** — место соискателя в списке рекрутёра по вакансии: в пределах свободных мест 1, дальше — доля соискателей специализации, которых он обходит.

`релевантность = 100 × √(подхожу × подходит) × (0,8 + 0,2 × очередь)`: среднее геометрическое не даёт перекосу в одну сторону поднять вакансию, очередь срезает не больше пятой части.

`GET /api/vacancies?user_id=<id>` возвращает выдачу, справочники и у каждой вакансии `record` — отклик или приглашение на неё — и `can_apply`. Нет специализации соискателя — 403. Спрятавшийся соискатель (`user_blocks/`) вакансии видит и может откликнуться.

«Откликнуться…» — `POST /api/vacancies/apply {"user_id", "vacancy_id", "answers"?}`: файл в `invitations/` с `type` `От кандидата рекрутеру`, `source` `vacancies`, снимком вакансии и релевантностью у рекрутёра. Вакансия без заданий — история `sent`; с заданиями `answers` обязательны (решение каждого, до 5000 символов), история `sent` → `task_sent_for_review`, решения — в `assignment_answers`. `applicant_seen` ставится сразу: свой отклик не уведомление, а новый статус от рекрутёра — уведомление у значка `4`. Повторный отклик или отклик на вакансию, куда соискателя уже пригласили, — 409; закрытая вакансия — 409; чужая специализация — 403; своя вакансия — 409. Отклик видят рекрутёр на вкладке «Обратная связь» проекта (окно `8`) и в окне «Соискатели» (`9`), соискатель — во вкладке «Отклики» окна «Приглашения» (`4`).

### Презентация

`app/assets/presentation/vacancies/slides.json` — семь слайдов-картинок (первый — тоже картинка, без видео), формат как у `applicants/slides.json`: `number`, `title`, `image_prompt` — промт для генерации картинки слайда 16:9, `image` — `{name, url}` файла картинки, `speaker_text` — текст докладчика, `audio` — `{name, url}` файла озвучки. Картинку слайда `N` сохраняйте в `app/assets/presentation/vacancies/<image.name>` (PNG 1920×1080), озвучку текста докладчика — в `app/assets/presentation/vacancies/<audio.name>` (WAV): имена `NN-<слаг>.png` и `NN-<слаг>.wav`, адреса `url` — `/app/assets/presentation/vacancies/<имя>`. Пока файлов нет, слайд показывает заглушку с путём и текст докладчика, листается кнопками. Сервер отдаёт `slides.json` как обычный файл: правка видна без пересборки.

## Профиль кандидата для рекрутёра

`GET /api/applicants/profile?user_id=<recruiter_id>&applicant_id=<candidate_id>` (`app/tools/candidate_profile.py`) — только чтение. Профиль доступен для кандидата из поиска либо через действующую связь приглашение → вакансия → собственный проект. Не рекрутёру — 403; отсутствующий или недоступный кандидат — 404. Окно `CandidateProfile.tsx` открывается из приглашений и откликов окна `8`, а также из поиска, списка по вакансии и графа команды окна `9`; закрытие возвращает к прежнему выбору.

Данные собираются без записи новых результатов:

- `user_specializations/`: все специализации соискателя. Для нескольких заявленных грейдов одной специализации используется `ranking._preference`, как в поиске. Отдельно показаны заявленный грейд и его источник, высший сданный тест и опровержение заявленного грейда по `ranking.grade_fit`.
- `user_fsp/`: только сохранённые `competencies` и `competitions`, уже принятые кандидатом. Названия берутся из справочников ФСП; степень 1–3 и баллы — из сохранённой сводки, как при ранжировании. Каждая компетенция раскрывает соревнования, которые её подтверждают. Предложенные будущие участия, отклонённые участия, ФСП ID и зерно генератора наружу не передаются.
- `user_tests/`: история всех специализаций, новые результаты первыми, включая отдельные события тестового зачёта (`credited_from`). Условия восстанавливаются по `task_key` через `grade_tests.from_key`; если ключ устарел, итог сохраняется в выдаче без условия. Ответы и код в этих файлах не хранятся; эталонные решения и ключи наружу не передаются.
- `invitations/`: условия и сохранённые `assignment_answers` заданий только по собственным действующим связям рекрутёра. Чужие проекты и решения не раскрываются. E-mail кандидата доступен только при наличии собственного приглашения или отклика в текущем статусе `accepted`.

Локальный снимок папки хранится в git; сервер не отдаёт эти файлы напрямую.

## user_fsp/

Файл `<user_id>.json` на каждого пользователя, создаёт `app/tools/fsp.py` по запросу `POST /api/fsp/save` к `app/tools/serve.py`. Это имитация: настоящего ФСП ID и реестра ФСП нет, сервер проверяет только формат идентификатора (маска `FSP-0000-0000`), а соревнования «находит» сам. Порядок такой:

1. В окне «Достижения в ФСП» (значок `1` в `additional_desktop_icons.json`) пользователь вводит ФСП ID. Не по маске — ошибка.
2. Окно показывает диаграмму последовательности: как ITinder связывался бы с ФСП через Keycloak и узнавал о новых соревнованиях. Сценарий и озвучка — `app/assets/presentation/fsp_link/scenes.json`.
3. Сервер «находит» от 1 до 5 прошедших соревнований из `fsp_competitions.json`, где в команде есть роль пользователя (по последней специализации соискателя, `fsp_team_roles.json`), без пересечения по датам. Итог команды случаен: работающее решение (55 %), призовое место (30 %) или победа (15 %).
4. Пользователь соглашается дополнить профиль — файл записывается. Отказывается — ничего не пишется.
5. Каждое соревнование из `fsp_future_competitions.json`, где есть роль пользователя, «случается» через `minutes_after_profile_link` минут после `linked_at`. Окно предлагает добавить его в профиль или отказаться; ответ записывается в этот же файл.

Тревога (красный «!») у значка ФСП — пока файла нет и пока есть созревшие будущие соревнования, которые пользователь ещё не добавил и не отклонил. Локальный снимок папки хранится в git; сервер не отдаёт эти файлы напрямую.

| Поле | Описание |
|---|---|
| `user_id` | Ссылка на `users/<id>.json`; совпадает с именем файла |
| `fsp_id` | ФСП ID, заглавными: `FSP-1234-5678` |
| `role_id`, `specialization` | Роль в команде (`fsp_team_roles.id`) и специализация, по которой она выбрана при связке. Будущие соревнования — в этой же роли |
| `linked_at` | Когда пользователь согласился дополнить профиль, ISO 8601 в UTC. От него отсчитываются минуты будущих соревнований |
| `seed` | Зерно генератора будущих участий: итог и технологии будущего соревнования при каждом открытии окна одни и те же |
| `competitions[]` | Соревнования в профиле: `competition_id` — из `fsp_competitions.json` или `fsp_future_competitions.json`; `source` — `registry` (найдено при связке) или `after_link` (будущее, после связки); `role_id`; `result` — `solution`, `prize` или `win`; `points` — балл итога (1, 2, 3) плюс балл уровня (региональное 0, межрегиональное 1, всероссийское и международное 2); `competencies` — что пользователь применял, `{kind: [id]}` по массивам `fsp_stack.json`; `added_at` |
| `declined[]` | Будущие соревнования, которые пользователь не стал добавлять: `{"competition_id", "declined_at"}`. Больше не предлагаются |
| `competencies[]` | Подтверждённые компетенции — сводка по `competitions`: `kind` и `id` (массив и запись `fsp_stack.json`), `points` — сумма баллов соревнований, где компетенция применялась, `degree` — степень подтверждения: 1 — базовая (от 1 балла), 2 — уверенная (от 3), 3 — высокая (от 6); `competitions` — где применялась |
| `updated_at` | Когда файл записан последний раз |

Что подтверждает роль: бэкендер — язык, СУБД и способы интеграции, фронтендер — язык и способы интеграции, тестировщик — язык и инструменты тестирования, аналитик — SQL, СУБД и способы интеграции. Из языков роли в стеке соревнования берётся один случайный (и SQL, если он есть и роль на нём пишет), из СУБД — одна случайная, способы интеграции и инструменты тестирования — все.
